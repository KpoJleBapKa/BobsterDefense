# Технічне завдання

## Модуль Strategic States для BobsterDefence

### 1. Загальна концепція

У плагін `BobsterDefence` необхідно інтегрувати систему автономних NPC-держав — `Strategic States`.

Максимальна кількість одночасно існуючих стратегічних держав:

**5 держав.**

Кожна держава повинна являти собою повноцінну автономну систему з:

* територією;
* населенням;
* економікою;
* ресурсами;
* житловим фондом;
* виробництвом;
* військом;
* обороною;
* технологічним розвитком;
* будівництвом;
* демографією;
* стратегічним AI;
* зовнішньою політикою;
* наступальними операціями;
* захопленням чужих територій;
* обороною власних територій;
* використанням озброєння BobsterDefence;
* взаємодією з територіями `TerritoryMap-1.6.0.jar`.

Базовим NPC населення є `Pillager`.

Принцип:

**State AI приймає стратегічні рішення, а окремі NPC виконують конкретні завдання.**

NPC не повинні самостійно вирішувати глобальні питання на кшталт:

* чи оголошувати війну;
* що будувати;
* куди запускати ракету;
* скільки створювати солдатів;
* яку територію захоплювати.

Це відповідальність центрального AI держави.

### 1.1 Термінологія та модель власника TerritoryMap

У межах цього ТЗ термін `гільдія` означає гравця, який володіє однією або кількома територіями TerritoryMap.

Окремої сутності або окремого плагіна гільдій немає.

Ідентичність гільдії:

```text
guildId = UUID гравця-власника TerritoryMap
guildName = актуальний owner-name гравця
territories = усі території TerritoryMap з тим самим owner UUID
```

TerritoryMap owner повинен мати тип:

```text
PLAYER
STRATEGIC_STATE
```

Термін `гільдія` застосовується тільки до `PLAYER`. Системний власник `STRATEGIC_STATE` представляє NPC-державу та не маскується під реального гравця.

Уся логіка, збереження, blacklist, війни та дипломатія повинні використовувати UUID власника. Ім'я використовується лише для відображення й пошуку в командах, оскільки гравець може змінити нік.

Якщо один гравець має кілька територій, вони вважаються землями однієї гільдії. Захоплення ведеться окремо для кожної території та її секторів, але дипломатичні відносини й заборона атак застосовуються до UUID власника загалом.

Якщо територія не має `owner UUID`, вона не є допустимою ціллю автоматичної війни до явного рішення адміністратора.

# 3. Ключовий принцип симуляції

Завантажені Minecraft-чанки не повинні визначати, чи існує і розвивається держава.

Необхідно мати два режими симуляції.

## 3.1 Physical Simulation

Використовується, коли територія держави прогружена гравцями.

У цьому режимі реально існують:

* Pillager;
* будівельники;
* солдати;
* фермери;
* патрулі;
* техніка;
* ракети;
* дрони.

NPC фізично:

* переміщуються;
* працюють;
* будують;
* воюють;
* охороняють;
* патрулюють;
* виконують завдання.

## 3.2 Virtual Simulation

Якщо чанки держави не прогружені, розвиток держави **НЕ ЗУПИНЯЄТЬСЯ**.

Замість фізичних NPC працює симулятор:

```text
StateSimulationEngine
```

Він повинен продовжувати:

* виробництво ресурсів;
* споживання ресурсів;
* народжуваність;
* смерть від голоду;
* будівництво;
* завершення заводів;
* виробництво зброї;
* формування армії;
* дослідження;
* відновлення після війни;
* стратегічне планування.

Наприклад:

```text
12:00

Wood = 250
Iron = 120
Food = 400

Farm #3 construction = 40%
```

Через 30 хвилин без жодного гравця поруч:

```text
12:30

Wood = 410
Iron = 184
Food = 530

Farm #3 construction = 100%
Barracks #1 construction = 35%
Population = 17
```

# 4. Матеріалізація змін unloaded-чанків

Важливо:

Minecraft не повинен постійно тримати всю державу прогруженою тільки заради будівництва.

Це створило б непотрібне навантаження.

Тому необхідна система:

```text
Virtual World Changes
```

Приклад.

AI вирішив:

```text
BUILD barracks_01
```

Будівля повинна знаходитися:

```text
X: 1520
Y: 71
Z: -440
```

Чанк не прогружений.

У такому випадку записується:

```text
VirtualBuilding
{
    stateId
    template
    location
    rotation
    constructionStarted
    constructionFinished
    materialized = false
}
```

Держава вважає казарму побудованою після завершення її virtual construction.

Але фізично блоки ще можуть не знаходитися у світі.

Коли відповідний чанк буде завантажено:

```text
ChunkLoadEvent
```

`VirtualConstructionManager` перевіряє:

```text
чи є тут pending world changes?
```

Якщо є:

```text
materialize()
```

і будівля вставляється у світ.

Таким чином:

**держава будується навіть у повністю unloaded області.**

# 5. Допустима короткочасна примусова загрузка

Для важливих операцій можна допустити короткочасне завантаження конкретних чанків самим плагіном.

Наприклад:

* необхідно фізично вставити схему;
* необхідно виконати вибух;
* починається реальна битва;
* летить ракета;
* необхідно оновити блоки.

Але категорично заборонено тримати:

```text
всю державу
+
всі її дороги
+
всю територію війни
```

постійно loaded.

# 6. State Core

Держава створюється спеціальним блоком Bedrock.

Команда:

```text
/bd states core give
```

Предмет:

```text
BEDROCK

Strategic State Core
```

PDC:

```text
bobsterdefence:item_type = state_core
```

PDC існує лише на предметі. Після встановлення BEDROCK зв'язок Core із державою зберігається в SQLite за `world + x + y + z`, оскільки BEDROCK не є TileState і не має власного PDC.

Повторне встановлення, повторний `BlockPlaceEvent` або рестарт не повинні створювати дубль держави. Координати Core мають унікальний індекс у сховищі.

Після встановлення:

```text
StrategicStateManager.createState(...)
```

створюється нова держава.

Перед створенням перевіряються:

* право `bobsterdefence.states.create`;
* ліміт `max-states`;
* дозволений світ;
* мінімальна відстань до інших State Core;
* відсутність перетину стартової зони з територією гравця;
* доступність write API TerritoryMap.

Стартова територія створюється через `TerritoryMapHook` як територія системного власника: `territoryName = state_<short UUID>`, `ownerUuid = state UUID`, `ownerName = state display name`, `ownerKind = STRATEGIC_STATE`. Технічна назва відповідає обмеженню TerritoryMap `[A-Za-z0-9_-]{1,32}`, а display name держави може містити пробіли. Форма і радіус задаються конфігом. Якщо TerritoryMap або його write API недоступні, нову державу створювати заборонено, але вже збережені держави завантажуються в безпечному режимі без експансії та війни.

`StateIdentityFactory` автоматично обирає унікальний стандартний колір і унікальну назву з конфігурованого списку. Якщо вільної назви немає, використовується шаблон `State-<short UUID>`. За ліміту 5 держав кожна активна держава повинна мати окремий колір.

# 18. Шаблони будівель

Необхідно використовувати готові шаблони.

Обов'язковий базовий формат — vanilla structure `.nbt`, який завантажується через Paper Structure API без зовнішніх залежностей. Підтримка Sponge `.schem` через WorldEdit або FAWE може бути додана як опційний адаптер.

Уся робота з шаблонами проходить через `StructureTemplateAdapter`. Реалізація вибирається за форматом файла та доступними плагінами.

Базові `.nbt` шаблони входять до BobsterDefence.jar і копіюються в data folder при першому запуску. Адміністратор може замінити їх власними файлами. Якщо потрібний шаблон відсутній або пошкоджений, держава не списує ресурси й не створює незавершувану будівлю. Операція переходить у стан `BLOCKED`, а причина виводиться в debug та `states.log`.

Наприклад:

```text
plugins/BobsterDefence/states/schematics/
```

Структура:

```text
house_01.nbt
house_02.nbt
farm_01.nbt
warehouse_01.nbt
mine_01.nbt
barracks_01.nbt
factory_01.nbt
missile_factory_01.nbt
drone_factory_01.nbt
air_defence_01.nbt
```

2. перевірити висоту;
3. перевірити нахил;
4. перевірити воду;
5. перевірити існуючі споруди;
6. перевірити TerritoryMap;
7. знайти вільну площу;
8. визначити rotation;
9. створити `BuildingInstance`.

# 21. Будівництво при unloaded-чанках

Будівництво продовжується віртуально.

Наприклад:

```text
14:00 = 20%
14:10 = 45%
14:20 = 75%
14:30 = 100%
```

Після 100%:

```text
building.status = COMPLETE
building.materialized = false
```

Після наступного завантаження чанку:

```text
materialized = true
```

Матеріалізація повинна бути ідемпотентною. Будівля має збережений footprint, перелік потрібних чанків і стани `PLANNED`, `BUILDING`, `COMPLETE_VIRTUAL`, `MATERIALIZING`, `MATERIALIZED`, `BLOCKED`.

Перед початком будівництва footprint резервується. Перед фізичною вставкою повторно перевіряються сторонні блоки та захист території. Заборонено перезаписувати будівлі гравців. Будівля, що перетинає кілька чанків, матеріалізується один раз після доступності всіх потрібних чанків, з лімітом змін блоків за тік.

# 23. Взаємодія з TerritoryMap

Необхідно реалізувати:

```text
TerritoryMapHook
```

BobsterDefence повинен отримувати:

```text
territoryId
ownerUuid
ownerName
ownerKind
world
parts
outer rings
holes
```

У цьому ТЗ:

```text
guildId = ownerUuid
guildName = ownerName
```

TerritoryMap 1.6.0 надає стабільний Bukkit Service та публікує events. API повинен містити:

* read-only snapshot усіх територій;
* пошук території за `world, x, z`;
* пошук усіх територій за `ownerUuid`;
* створення стартової території системного власника;
* атомарна зміна власника після повного захоплення;
* збереження `ownerKind = PLAYER|STRATEGIC_STATE`;
* події створення, зміни, видалення та зміни власника території.

API реєструється через Bukkit Services. BobsterDefence підключається до нього через `softdepend: TerritoryMap`.

Як fallback, якщо API недоступний, `TerritoryMapHook` може читати `plugins/TerritoryMap/territories.yml` тільки для read-only функцій:

* повітряна тривога;
* пошук територій;
* визначення власника;
* вибір цілей.

У fallback-режимі зміна власника TerritoryMap заборонена, а секторальна окупація залишається лише у внутрішньому overlay BobsterDefence. Прямий запис BobsterDefence у чужий `territories.yml` заборонений.

StrategicStates не повинен напряму розкидати виклики TerritoryMap по всьому коду.

Уся взаємодія повинна проходити через:

```text
TerritoryMapHook
```

# 24. Глобальне керування війною

# 25. Поведінка attacks off

Після:

```text
/bd states attacks off
```

забороняється:

```text
DeclareWar
StartInvasion

LaunchOffensiveDrone
CaptureEnemyPoint
```

Але дозволяється:

```text
Economy
Construction
Population

```

Самооборона означає відповідь на безпосередню загрозу всередині власної території або поруч із NPC. Вона не дозволяє переслідувати ворога на його території, захоплювати сектори чи здійснювати ракетні та дронові удари.

# 26. Активна атака в момент вимкнення

Якщо адміністратор вводить:

```text
/bd states attacks off
```

коли напад уже триває, рекомендується режим:

```text
immediate ceasefire
```

Тобто:

* нові ракети не запускаються;
* дрони наступального типу повертаються/видаляються;
* війська припиняють просування;
* захоплення контрольних точок зупиняється;
* штурмові загони переходять у стан `RETREAT`;
* вже запущені ракети бажано не телепортувати назад, але їх можна або дозволити завершити політ, або видалити відповідно до конфігу.

Конфіг:

```yaml
strategic-states:
  attacks:
    on-disable:
      cancel-active-invasions: true
      cancel-active-drones: true
      destroy-flying-missiles: false
      force-retreat: true
```

```text
OFF
```

# 28. Безпечне значення за замовчуванням

Значення конфігу:

```yaml
strategic-states:
  attacks:
    enabled-on-first-start: false
```

Цей ключ використовується тільки при першому створенні бази. Надалі фактичний `attacksEnabled` читається зі SQLite й не перезаписується значенням конфігу після рестарту або reload.

Тобто адміністратор сам активує війни:

```text
/bd states attacks on
```

# 29. Виключення окремих гільдій

Необхідно мати список:

```text
Protected Guilds
```

Запис у списку — UUID гравця-власника території. Команда приймає нік гравця або назву його території, знаходить відповідний `ownerUuid` через TerritoryMap і зберігає саме UUID.

Команда:

```text
/bd states guild exclude <player|territory>
```

Наприклад:

```text
/bd states guild exclude Kroll_Empire
```

Після цього жодна NPC-держава не має права:

* оголошувати їй війну;
* запускати ракети;
* запускати дрони;
* вторгатися;
* захоплювати контрольні точки;
* обстрілювати її територію.

Звичайна ближня самооборона NPC від гравця із protected guild дозволена лише в безпосередній зоні загрози. Вона не може переходити у війну, переслідування, захоплення або стратегічний удар.

# 35. Вибір ворога

`TargetSelectionAI` групує всі території TerritoryMap з `ownerKind = PLAYER` за `ownerUuid`. Кожна група є однією гільдією гравця. Території з `ownerKind = STRATEGIC_STATE` обробляються окремою логікою state-vs-state.

Для решти рахується:


# 49. Інтеграція з TerritoryMap

TerritoryMap 1.6.0 має модель `одна територія = один ownerUuid` і не має власності окремих секторів. Тому BobsterDefence завжди веде власний internal overlay:

```text
SectorOwnership
```

Під час часткової окупації вихідний полігон TerritoryMap не змінюється. Overlay зберігає початкового власника, поточного контролера, прогрес і стан кожного сектора.

Після:

```text
100% territory captured
```

`TerritoryMapHook` атомарно змінює owner території через Bukkit Service API. Для NPC-держави ownerUuid дорівнює UUID Strategic State, а ownerName — назві держави. API TerritoryMap повинен явно підтримувати системного власника, який не зобов'язаний бути UUID реального Minecraft-гравця.

Якщо BobsterDefence працює у fallback-режимі без write API, повне захоплення фіксується у внутрішньому overlay, записується попередження в лог, а TerritoryMap залишається без змін до появи API або ручної дії адміністратора.

# 51. Оборона власної держави NPC

Strategic State повинна мати власні контрольні точки.

При нападі гравців або іншої стратегічної держави:

```text
DefenceAI
```

повинен:

* збирати війська;
* посилювати фронт;
* підтягувати резерв;
* запускати оборонні дрони;
* активувати ППО;
* перерозподіляти ресурси.

# 52. Знищення держави

Основна умова:

```text
livingPopulation == 0
```

Держава знищена тільки після транзакційно підтвердженої смерті всіх записів Citizen. Unload чанку, невдала матеріалізація, відсутність entity після рестарту або тимчасова помилка пошуку не вважаються смертю.

Після цього:

```text
state.status = DESTROYED
```

---

# 53. State Core

Core не повинен автоматично означати миттєве знищення держави, якщо твоєю основною умовою є смерть усіх жителів.

Але його можна зробити стратегічно важливим.

Наприклад після руйнування Core:

```text
-50% stability
-50% production
new population disabled
command functions disabled
```

поки Core не буде відновлено.

BEDROCK не ламається стандартними інструментами, тому пошкодження та відновлення Core реалізуються окремою механікою взаємодії StrategicStates. Звичайний `BlockBreakEvent` не є єдиним способом знищення Core.

# 55. BobsterDefence Weapon Integration

NPC не повинні мати окрему імітовану систему ракет.

Необхідно використовувати спільні низькорівневі механіки:

```text
Missile launch/flight/collision/effects/interception
Drone model/flight/collision/explosion/interception
Air defence targeting/interceptors
```

через внутрішній API BobsterDefence.

Поточні player-facing методи не є цим API: запуск ракети прив'язаний до `Player` і dispenser, а FPV-дрон — до керування гравцем у spectator mode. Потрібно винести спільне ядро та додати:

```text
MissileLaunchRequest
AutonomousDroneMission
CombatPrincipal
```

`CombatPrincipal` представляє гравця або Strategic State. Усі ракети, дрони та перехоплювачі мають зберігати тип і UUID власника, щоб єдина система allegiance визначала `friendly/hostile`.

NPC використовує віртуальний арсенал замість інвентаря гравця, але після списання боєприпасу створюється той самий фізичний projectile і застосовуються ті самі ефекти, collision та interception.

```text
AttackPolicyManager.canAct(attacker, target, context, action)
```

перевіряється ще раз.

Тобто навіть якщо WarPlan був створений раніше, але за 10 секунд до пуску адмін виключив гільдію:

```text
launch = CANCELLED
```

# 75A. Удари гравців по Strategic State

Кожна детонація FPV-дрона або балістичної ракети в межах TerritoryMap-території Strategic State створює `StrategicImpact` із такими даними:

```text
State UUID
CombatPrincipal атакувальника
WeaponType
ExplosionPower
World / XYZ
GroundImpact
Timestamp
```

Фізичний шар залишається джерелом фактичного руйнування блоків і смерті завантажених Citizen. Стратегічний шар додатково:

* зменшує stability;
* знищує частину ресурсних запасів;
* ураховує пошкодження будівель після появи Building System;
* накопичує threat до конкретного UUID атакувальника;
* зберігає удар і threat у SQLite.

Вибух високо над поверхнею записується як загроза, але не списує ресурси й не пошкоджує будівлі. Перехоплений боєприпас біля землі може завдати звичайних наслідків відповідно до фактичної точки та сили вибуху.

Threat поступово зменшується за конфігурованим half-life. Один випадковий удар не повинен автоматично створювати нескінченну війну.

Правила відповіді:

```text
attacks = OFF                         -> локальна самооборона, без стратегічної відповіді
attacks = ON, threat нижче порога     -> тривога й оборонна готовність
attacks = ON, threat вище порога      -> кандидат на майбутню операцію відплати
protected guild                       -> тільки локальна самооборона
friendly CombatPrincipal              -> не вважається ворожим ударом
```

Удар не змінює TerritoryMap owner і не запускає захоплення секторів. Для цього потрібна окрема війна та наземний контроль.

# 91. Асинхронність

Математичні розрахунки:

* target scoring;
* economy;
* AI decisions;
* database work;

по можливості виконувати поза Minecraft main thread.

Але Bukkit/Paper world API не викликати довільно з async thread.

Paper має scheduler-механізми для відкладених/повторних задач, а також окремий async scheduler у сучасному API.

Доступ до SQLite виконується через один контрольований async executor. Bukkit/Paper API, читання блоків, створення сутностей і зміна світу виконуються тільки на main thread. Для target scoring main thread порціями формує immutable snapshot, після чого математичний scoring може виконуватися async.

# 98. AttackPolicy як обов'язковий центральний gate

Усі наступальні операції повинні пройти:

```text
AttackPolicyManager
```

Центральний gate отримує контекст операції:

```java
boolean canAct(CombatPrincipal attacker, CombatPrincipal target, ActionContext context, OffensiveAction action) {
    if (!strategicStatesEnabled) {
        return false;
    }
    if (context == ActionContext.OFFENSIVE && !attacksEnabled) {
        return false;
    }
    if (context == ActionContext.OFFENSIVE && protectedOwnerUuids.contains(target.id())) {
        return false;
    }
    return true;
}
```

`DEFENSIVE` дозволяє лише локальну самооборону. Захоплення секторів, переслідування на чужій території та стратегічні удари завжди мають контекст `OFFENSIVE`.

Але перевірка здійснюється:

1. при виборі ворога;
2. при оголошенні війни;
3. перед мобілізацією;
4. перед заходом у сектор;
5. перед стартом захвату;
6. перед запуском дрона;
7. перед запуском ракети.

Це захищає від race conditions та зміни адміном конфігурації під час активної війни.

# 102. Критерії готовності

Система вважається повністю реалізованою, якщо можна провести такий тест:

1. Адміністратор ставить `State Core`.

2. З'являються 4-6 Pillager.

3. NPC починають початковий розвиток.

4. Гравець залишає район.

5. Чанки unload.

6. Через 30 хвилин гравець повертається.

7. Держава за цей час:

   * накопичила ресурси;
   * збільшила населення;
   * завершила будівництво.

8. Будівлі матеріалізуються у світі.

9. Держава досягає Level 3+.

10. `attacks = OFF`.

11. Держава не атакує нікого.

12. Адміністратор виконує:

```text
/bd states attacks on
```

13. Держава аналізує TerritoryMap.

14. Protected guilds ігноруються.

15. Обирається допустима гільдія.

16. Держава готує армію.

17. Скануються стратегічні споруди.

18. Велика кам'яна споруда отримує підвищений TargetScore.

19. Запускається реальна ракета BobsterDefence.

20. Ракету може перехопити ППО BobsterDefence.

21. NPC переходять у наземний наступ.

22. Захоплюють першу контрольну точку.

23. У внутрішньому `SectorOwnership` переходить тільки один сектор; власник усієї території TerritoryMap ще не змінюється.

24. Фронт просувається.

25. Наступний сектор захоплюється окремо.

26. Адміністратор виконує:

```text
/bd states attacks off
```

27. Наступ припиняється.

28. Економіка NPC держави продовжує працювати.

29. Адміністратор виконує:

```text
/bd states guild exclude Solaria
```

30. Solaria більше ніколи не обирається ціллю до виконання:

```text
/bd states guild include Solaria
```

31. Після рестарту `attacksEnabled`, protected owner UUID, війни, сектори, Citizens і будівлі відновлюються без втрати стану.

32. Повторне завантаження чанку не створює дублікати Citizen, армій або будівель.

33. Часткове захоплення змінює тільки `SectorOwnership` BobsterDefence і не передає всю територію TerritoryMap.

34. Після захоплення всіх секторів TerritoryMap отримує `ownerUuid = state UUID` та `ownerKind = STRATEGIC_STATE` через Service API.

35. Якщо write API TerritoryMap недоступний, створення нової держави блокується з чітким повідомленням, а решта BobsterDefence продовжує працювати.

# 103. Головний архітектурний принцип

Уся система повинна будуватися навколо трьох різних рівнів:

```text
STRATEGIC LAYER
```

Держава:

* приймає рішення;
* веде економіку;
* планує;
* воює;
* керує територіями.

```text
SIMULATION LAYER
```

Обчислює:

* ресурси;
* населення;
* production;
* construction;
* virtual movement;
* війни.

```text
PHYSICAL LAYER
```

Minecraft:

* Pillager;
* блоки;
* ракети;
* дрони;
* explosions;
* particles;
* actual combat.

Головне правило:

**Physical Layer ніколи не є джерелом існування держави.**

Він лише візуалізує Strategic/Simulation Layer.

Саме завдяки цьому Strategic State продовжуватиме жити, будуватися і розвиватися навіть тоді, коли жоден її чанк не завантажений.

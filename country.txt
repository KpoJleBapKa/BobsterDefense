# Технічне завдання

## Модуль Strategic States для BobsterDefence

### 1. Загальна концепція

У плагін `BobsterDefence` необхідно інтегрувати систему автономних NPC-держав — `Strategic States`.

Максимальна кількість одночасно існуючих стратегічних держав:

**5 держав.**

Кожна держава повинна являти собою повноцінну автономну систему з:

* територією;
* населенням;
* економікою;
* ресурсами;
* житловим фондом;
* виробництвом;
* військом;
* обороною;
* технологічним розвитком;
* будівництвом;
* демографією;
* стратегічним AI;
* зовнішньою політикою;
* наступальними операціями;
* захопленням чужих територій;
* обороною власних територій;
* використанням озброєння BobsterDefence;
* взаємодією з територіями `TerritoryMap-1.5.0.jar`.

Базовим NPC населення є `Pillager`.

Принцип:

**State AI приймає стратегічні рішення, а окремі NPC виконують конкретні завдання.**

NPC не повинні самостійно вирішувати глобальні питання на кшталт:

* чи оголошувати війну;
* що будувати;
* куди запускати ракету;
* скільки створювати солдатів;
* яку територію захоплювати.

Це відповідальність центрального AI держави.

# 3. Ключовий принцип симуляції

Завантажені Minecraft-чанки не повинні визначати, чи існує і розвивається держава.

Необхідно мати два режими симуляції.

## 3.1 Physical Simulation

Використовується, коли територія держави прогружена гравцями.

У цьому режимі реально існують:

* Pillager;
* будівельники;
* солдати;
* фермери;
* патрулі;
* техніка;
* ракети;
* дрони.

NPC фізично:

* переміщуються;
* працюють;
* будують;
* воюють;
* охороняють;
* патрулюють;
* виконують завдання.

## 3.2 Virtual Simulation

Якщо чанки держави не прогружені, розвиток держави **НЕ ЗУПИНЯЄТЬСЯ**.

Замість фізичних NPC працює симулятор:

```text
StateSimulationEngine
```

Він повинен продовжувати:

* виробництво ресурсів;
* споживання ресурсів;
* народжуваність;
* смерть від голоду;
* будівництво;
* завершення заводів;
* виробництво зброї;
* формування армії;
* дослідження;
* відновлення після війни;
* стратегічне планування.

Наприклад:

```text
12:00

Wood = 250
Iron = 120
Food = 400

Farm #3 construction = 40%
```

Через 30 хвилин без жодного гравця поруч:

```text
12:30

Wood = 410
Iron = 184
Food = 530

Farm #3 construction = 100%
Barracks #1 construction = 35%
Population = 17
```

# 4. Матеріалізація змін unloaded-чанків

Важливо:

Minecraft не повинен постійно тримати всю державу прогруженою тільки заради будівництва.

Це створило б непотрібне навантаження.

Тому необхідна система:

```text
Virtual World Changes
```

Приклад.

AI вирішив:

```text
BUILD barracks_01
```

Будівля повинна знаходитися:

```text
X: 1520
Y: 71
Z: -440
```

Чанк не прогружений.

У такому випадку записується:

```text
VirtualBuilding
{
    stateId
    template
    location
    rotation
    constructionStarted
    constructionFinished
    materialized = false
}
```

Держава вважає казарму побудованою після завершення її virtual construction.

Але фізично блоки ще можуть не знаходитися у світі.

Коли відповідний чанк буде завантажено:

```text
ChunkLoadEvent
```

`VirtualConstructionManager` перевіряє:

```text
чи є тут pending world changes?
```

Якщо є:

```text
materialize()
```

і будівля вставляється у світ.

Таким чином:

**держава будується навіть у повністю unloaded області.**

# 5. Допустима короткочасна примусова загрузка

Для важливих операцій можна допустити короткочасне завантаження конкретних чанків самим плагіном.

Наприклад:

* необхідно фізично вставити схему;
* необхідно виконати вибух;
* починається реальна битва;
* летить ракета;
* необхідно оновити блоки.

Але категорично заборонено тримати:

```text
всю державу
+
всі її дороги
+
всю територію війни
```

постійно loaded.

# 6. State Core

Держава створюється спеціальним блоком Bedrock.

Команда:

```text
/bd state core give
```

або:

```text
/bd state createitem
```

Предмет:

```text
BEDROCK

Strategic State Core
```

PDC:

```text
bobsterdefence:item_type = state_core
```

Після встановлення:

```text
StrategicStateManager.createState(...)
```

створюється нова держава.

# 19. Вибір місця будівництва

`ConstructionAI` повинен:

1. знайти область біля існуючого поселення;
2. перевірити висоту;
3. перевірити нахил;
4. перевірити воду;
5. перевірити існуючі споруди;
6. перевірити TerritoryMap;
7. знайти вільну площу;
8. визначити rotation;
9. створити `BuildingInstance`.

# 23. Взаємодія з TerritoryMap

Необхідно реалізувати:

```text
TerritoryMapHook
```

BobsterDefence повинен отримувати:

```text
territoryId
guildId
guildName
world
polygon/regions
owner
```

Конкретний механізм hook залежить від того, який API фактично експортує `TerritoryMap-1.5.0.jar`.

Якщо прямого API немає, реалізувати адаптер через:

* Bukkit services;
* events;
* reflection;
* або винести невеликий API у TerritoryMap.

StrategicStates не повинен напряму розкидати виклики TerritoryMap по всьому коду.

Уся взаємодія повинна проходити через:

```text
TerritoryMapHook
```

# 26. Активна атака в момент вимкнення

Якщо адміністратор вводить:

```text
/bd states attacks off
```

коли напад уже триває, рекомендується режим:

```text
immediate ceasefire
```

Тобто:

* нові ракети не запускаються;
* дрони наступального типу повертаються/видаляються;
* війська припиняють просування;
* захоплення контрольних точок зупиняється;
* штурмові загони переходять у стан `RETREAT`;
* вже запущені ракети бажано не телепортувати назад, але їх можна або дозволити завершити політ, або видалити відповідно до конфігу.

Конфіг:

```yaml
strategic-states:
  attacks:
    on-disable:
      cancel-active-invasions: true
      cancel-active-drones: true
      destroy-flying-missiles: false
      force-retreat: true
```

# 32. Перевірка захищеної гільдії

Перед будь-якою наступальною дією викликається:

```java
attackPolicy.canAttack(guildId)
```

Перевірка має бути централізованою.

Не можна окремо перевіряти blacklist у MissileManager, DroneManager, WarManager тощо.

Правильна схема:

```text
AttackPolicyManager
```

із методом:

```text
canAttackGuild()
```

# 34. Автоматичне нічне відключення

Основною вимогою є команда.

Але закласти можливість майбутнього scheduler:

```yaml
attack-schedule:
  enabled: false
```

Наприклад:

```text

```

Це не обов'язково реалізовувати в першій версії, але архітектура не повинна цьому заважати.

# 51. Оборона власної держави NPC

# 53. State Core

Core не повинен автоматично означати миттєве знищення держави, якщо твоєю основною умовою є смерть усіх жителів.

# 98. AttackPolicy як обов'язковий центральний gate

Усі наступальні операції повинні пройти:

```text
AttackPolicyManager
```

Псевдологіка:

```java
boolean canAttack(Guild guild) {

    if (!strategicStatesEnabled)
        return false;

    if (!attacksEnabled)
        return false;

    if (excludedGuilds.contains(guild.getId()))
        return false;

    return true;
}
```

Але перевірка здійснюється:

1. при виборі ворога;
2. при оголошенні війни;
3. перед мобілізацією;
4. перед заходом у сектор;
5. перед стартом захвату;
6. перед запуском дрона;
7. перед запуском ракети.

Це захищає від race conditions та зміни адміном конфігурації під час активної війни.

# 102. Критерії готовності

Система вважається повністю реалізованою, якщо можна провести такий тест:

1. Адміністратор ставить `State Core`.

2. З'являються 4-6 Pillager.

3. NPC починають початковий розвиток.

4. Гравець залишає район.

5. Чанки unload.

6. Через 30 хвилин гравець повертається.

7. Держава за цей час:

   * накопичила ресурси;
   * збільшила населення;
   * завершила будівництво.

8. Будівлі матеріалізуються у світі.

9. Держава досягає Level 3+.

10. `attacks = OFF`.

11. Держава не атакує нікого.

12. Адміністратор виконує:

```text
/bd states attacks on
```

13. Держава аналізує TerritoryMap.

14. Protected guilds ігноруються.

15. Обирається допустима гільдія.

16. Держава готує армію.

17. Скануються стратегічні споруди.

18. Велика кам'яна споруда отримує підвищений TargetScore.

19. Запускається реальна ракета BobsterDefence.

20. Ракету може перехопити ППО BobsterDefence.

21. NPC переходять у наземний наступ.

22. Захоплюють першу контрольну точку.

23. Переходить тільки один сектор TerritoryMap.

24. Фронт просувається.

25. Наступний сектор захоплюється окремо.

26. Адміністратор виконує:

```text
/bd states attacks off
```

27. Наступ припиняється.

28. Економіка NPC держави продовжує працювати.

29. Адміністратор виконує:

```text
/bd states guild exclude Solaria
```

30. Solaria більше ніколи не обирається ціллю до виконання:

```text
/bd states guild include Solaria
```

# 103. Головний архітектурний принцип

Уся система повинна будуватися навколо трьох різних рівнів:

```text
STRATEGIC LAYER
```

Держава:

* приймає рішення;
* веде економіку;
* планує;
* воює;
* керує територіями.

```text
SIMULATION LAYER
```

Обчислює:

* ресурси;
* населення;
* production;
* construction;
* virtual movement;
* війни.

```text
PHYSICAL LAYER
```

Minecraft:

* Pillager;
* блоки;
* ракети;
* дрони;
* explosions;
* particles;
* actual combat.

Головне правило:

**Physical Layer ніколи не є джерелом існування держави.**

Він лише візуалізує Strategic/Simulation Layer.

Саме завдяки цьому Strategic State продовжуватиме жити, будуватися і розвиватися навіть тоді, коли жоден її чанк не завантажений.
